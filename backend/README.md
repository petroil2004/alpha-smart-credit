# Backend: черновики, отправка и просмотр сотрудником

Сервер реализует согласованный с frontend API для демонстрационного входа и черновиков. Данные хранятся в PostgreSQL. Реализованы `DRAFT` и регистрация оборотного кредита в `UNDER_REVIEW`, шесть синтетических клиентов и сотрудник, cookie-сессия, изоляция компаний, защита от повторных операций и версия заявки.

Также реализованы авторизованный каталог трёх продуктов и расчёт платежа для оборотного кредита и оборудования. Работают отправка всех трёх продуктов, серверный расчёт овердрафта при отправке, демонстрационный скоринг и решение сотрудника. Подпись и выдача денег не реализованы. Помощник подключается через OpenAI-совместимый API с LLM_BASE_URL/LLM_API_KEY/LLM_MODEL, по умолчанию выключен. Чат в интерфейсе подключён; реальную модель нужно настроить отдельно.

## Каталог и калькулятор

После демонстрационного входа доступны `GET /api/v1/products` и `POST /api/v1/calculations/annuity`. Суммы передаются строками, срок — целым числом. Пример тела: `{"product_code":"working_capital","amount_rub":"3000000.00","term_months":36}`. Ответ: платёж `119279.48`, итог `4294061.28`, переплата `1294061.28` ₽ и версия каталога. Полный формат — в [контракте калькулятора](../docs/technical/loan-calculator-contract.md).

Ставки и ограничения находятся в `app/product_catalog.py`, вычисления — в `app/calculator.py`. Денежные промежуточные результаты не округляются, платёж округляется по ROUND_HALF_UP; итог упрощённого калькулятора равен платежу × месяцы. Полный график платежей не строится. Это демонстрационные условия, не решение об одобрении.

Расчёт не сохраняет заявку и не меняет её версию. Продуктовые диапазоны проверяются для расчёта; неполный черновик и сумму вне диапазона можно сохранить, как раньше. Миграций БД для этих методов нет.

## Запуск

Требуется Docker Compose. Из корня репозитория:

```bash
cp .env.example .env
docker compose up --build -d
curl http://127.0.0.1:8000/api/v1/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

PostgreSQL не публикуется на хост. Backend доступен только на `127.0.0.1:8000`; frontend Vite по умолчанию перенаправляет `/api` на этот адрес.

## Проверки на PostgreSQL

При стандартных демонстрационных настройках один раз создайте отдельную тестовую БД:

```bash
docker compose exec -T db psql -U credit -d postgres -c 'CREATE DATABASE credit_cabinet_tests'
```

Затем запускайте проверки так:

```bash
docker compose run --rm --no-deps \
  -e DATABASE_URL=postgresql+psycopg://credit:credit@db:5432/credit_cabinet_tests \
  backend pytest -q
```

При изменённых имени пользователя или пароле в `.env` замените демонстрационные значения в командах. Повторно создавать существующую тестовую БД не нужно.

Проверки запускаются внутри отдельного контейнера backend против PostgreSQL-сервиса `db`. SQLite не применяется. Тесты очищают схему указанной через `DATABASE_URL` базы; имя тестовой базы обязано оканчиваться на `_tests`. Не направляйте их на `credit_cabinet` с вашими сохранёнными черновиками или на другую рабочую БД.

Проверить сохранение после перезапуска вручную:

```bash
docker compose restart backend
```

После команды браузер с уже выданной cookie должен получить `GET /api/v1/me` со статусом 200, а черновик остаться в `GET /api/v1/applications`. Для полного удаления демонстрационных данных используйте `docker compose down -v`.

## Демонстрационные запросы

Вход первого клиента:

```bash
curl -i -c cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"account_id":"demo-client-1"}' \
  http://127.0.0.1:8000/api/v1/auth/demo-login
```

Ответ: 200 и объект `user`/`company`; заголовок `Set-Cookie` содержит HttpOnly `credit_cabinet_session`.

Создание пустого черновика:

```bash
curl -b cookies.txt \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 4f65e9d1-71fb-4ae8-8ecb-900d4d804b3f' \
  -d '{}' \
  http://127.0.0.1:8000/api/v1/applications
```

Ответ: 201 и объект Application со статусом `DRAFT`, версией `1` и пустыми полями. Повтор того же запроса с тем же ключом вернёт 200 и тот же `id`.

Изменение черновика (подставьте `APPLICATION_ID` из ответа):

```bash
curl -b cookies.txt \
  -X PATCH \
  -H 'Content-Type: application/json' \
  -d '{"version":1,"product_code":"working_capital","amount_rub":"125000.00","term_months":12}' \
  http://127.0.0.1:8000/api/v1/applications/APPLICATION_ID
```

Ответ: 200, `amount_rub` в формате строки с двумя знаками и `version: 2`. Если указанная версия устарела, сервер возвращает 409 `VERSION_CONFLICT` и не меняет заявку. Неприменимые к продукту поля возвращают 422 `VALIDATION_ERROR`.

Проверка версии и запись выполняются с блокировкой строки PostgreSQL: при двух одновременных сохранениях одной версии один запрос получает 200, второй — 409. Второй запрос не перезаписывает результат первого.

Суммы хранятся в `Numeric(18,2)` и технически не могут превышать `9999999999999999.99`; дни и месяцы хранятся в `Integer` и не могут превышать `2147483647`. Превышение возвращает 422 с указанием поля, не меняя черновик или его версию. Это вместимость хранения, а не кредитные лимиты: окончательные ограничения продуктов согласовываются отдельно.

Тесты включают одновременные запросы с реальными блокировками PostgreSQL, переполнение обоих денежных и обоих целочисленных полей и сохранение граничных значений без потери точности. Для проверки используйте отдельную тестовую БД: тестовая очистка схемы удаляет её содержимое.

## Адреса для frontend

Все запросы frontend идут через `/api/v1` того же origin:

- `POST /api/v1/auth/demo-login` — 200 и cookie;
- `GET /api/v1/me` — 200, без cookie 401 `UNAUTHENTICATED`;
- `POST /api/v1/auth/logout` — 204;
- `GET /api/v1/applications` — 200 `{ "items": [...] }`;
- `POST /api/v1/applications` — 201, либо 200 при повторе `Idempotency-Key`;
- `GET /api/v1/applications/{id}` — 200 для своей заявки, иначе 404 `NOT_FOUND`;
- `PATCH /api/v1/applications/{id}` — 200, 409 при устаревшем `version`, 422 для неверных полей.

OpenAPI и Swagger доступны по `http://127.0.0.1:8000/docs`.

## Удаление неотправленного черновика

`DELETE /api/v1/applications/{id}?version=N` удаляет только свою заявку DRAFT с актуальной версией. После 204 её нет в списке и по прямому адресу. Отправленные заявки не удаляются. Защита компании, статуса и версии проверяется сервером независимо от наличия кнопки.

Первоначальный ключ создания сохраняется как квитанция с пустым `application_id`: повтор POST возвращает 410 APPLICATION_DELETED, не создавая заявку снова. При старте `app/schema_compat.py` автоматически и повторяемо снимает только ограничение NOT NULL с этого столбца в существующей базе. Заявки, сессии и прочие ограничения сохраняются. Пересборка/перезапуск backend применяет это совместимое изменение; очищать базу или volume не нужно. Проверки миграции и удаления выполняются только на отдельной тестовой базе.

## Отправка и доступ сотрудника

Новые методы описаны в [контракте отправки](../docs/technical/submission-contract.md): GET `/api/v1/company-profile`, POST `/api/v1/applications/{id}/submit`, GET `/api/v1/staff/applications`, GET `/api/v1/staff/applications/{id}`. Демо-вход `demo-staff-1` возвращает роль STAFF и company:null; клиентский ответ сохраняет объект своей компании. Клиентские действия требуют CLIENT, сотруднические — STAFF (403 при неверной роли).

Отправка блокирует строку заявки, проверяет владельца/версию/подтверждение и действующие условия каталога, повторно считает платёж. Одной транзакцией сохраняет неизменяемый JSONB-снимок, квитанцию повтора и два события DRAFT → SUBMITTED → UNDER_REVIEW. Версия увеличивается один раз. Вторая запись истории выполняется системой, а не сотрудником, без утверждений о выполненном скоринге. Сохраняется период будущего финансового рассмотрения — шесть завершённых календарных месяцев по Europe/Moscow; неизвестных финансовых значений не выдумываем.

Повтор прежнего ключа/тела возвращает результат без дубля; ключ уникален для автора. Иное содержание того же ключа — 409 IDEMPOTENCY_CONFLICT. Версии профиля/каталога проверяются отдельно. Списки возвращают сводку; снимок и история доступны только в защищённой подробной карточке. Сотрудник не видит DRAFT и не может создать, изменить или отправить клиентскую заявку.

При запуске создаются новые таблицы `application_submissions`/`application_events`; повторяемое обновление снимает NOT NULL только с company_id/company_name аккаунта для STAFF. Клиент без собственной компании не получает клиентских прав. Прежние черновики, сессии и квитанции создания не переписываются. Для обновления используйте существующее имя compose-проекта; сбрасывать БД/volume не требуется.

[Отчёт приёмки](../docs/technical/2026-10-24-submit-review-verification.md) различает автоматические проверки отдельной БД и ручную работу с настоящим сервером.


## Уточнения, переписка и документы

Реализован цикл `UNDER_REVIEW → NEEDS_INFO → UNDER_REVIEW`: запрос сотрудника, автосохраняемый черновик ответа, независимые сообщения и явная отправка клиентом. Одновременно открыт один запрос, после закрытия можно создать следующий. Исходные снимок/расчёт/финансовый период не меняются; новые сведения — SELF_REPORTED. Статус и версия Application меняются только на переходах; revision запроса — при тексте/файлах/закрытии. Сообщения не меняют revision.

Новые таблицы `info_requests`, `info_messages`, `info_operations`, `info_attachments` создаются повторяемо при старте без очистки прежних таблиц. PDF/TXT до 5 МиБ хранятся в bytea PostgreSQL, содержимое не входит в JSON карточки и не загружается для сводки. Поток ограничивается до записи, проверяются имя/тип/расширение/содержимое; до пяти активных файлов. Это проверка формата, а не подлинности. Скачивание требует роли и прав на заявку, использует attachment/nosniff. Открепление сохраняет квитанцию и запрещает скачивание/позднее восстановление файла.

Все изменения сериализуются блокировкой строки заявки. Создание, сообщение и отправка ответа имеют сохранённые UUID-квитанции; повтор возвращает текущее состояние без дублей, даже после следующего запроса. Файл повторяется по UUID и хешу содержимого, после открепления возвращается 410. Права проверяются до поиска повтора. Пересборка backend использует прежний compose-проект и PostgreSQL volume, без сброса данных.

[Полный контракт](../docs/technical/clarifications-contract.md), [фактический отчёт](../docs/technical/2026-10-24-clarifications-verification.md). Скоринг, чтение содержимого моделью и структурированная финансовая анкета не входят в этот этап.


## Демо-профили и финансы

`GET /api/v1/company-profile` для CLIENT возвращает расширенный профиль и шесть завершённых месяцев по Europe/Moscow. Данные подготовлены, а не получены настоящим запросом в ФНС/банк. ИНН/ОКВЭД пока null. `CompanyData` и `CompanyMonth` добавляются при старте без сброса прежних таблиц. Фиксированные суммы находятся в `app/demo_data/company-profiles.json`; `demo_profiles.py` создаёт отсутствующие аккаунты/полный набор одной транзакцией под advisory-блокировкой PostgreSQL. Повторный старт, параллельный старт и смена версии файла не перезаписывают существующее. Несовпадающий аккаунт диагностируется и пропускается. Автоматического ремонта неполного набора нет.

Первичная дата подготовки и месяцы сохраняются. На новом календарном месяце API показывает актуальный период с null там, где нет сохранённой строки: старые суммы не переносятся на новые даты. Среднее только для полного ряда, Decimal/ROUND_HALF_UP; долговые платежи хранятся отдельно и не добавляются в операционные расходы. Неполные финансы не запрещают подачу корректного оборотного запроса.

Единая SQL-проекция профиля/месяцев и полная SHA256-версия позволяют подтверждать именно показанные сведения. При отправке дата берётся один раз; период профиля и снимка совпадают. Изменение источника/пропуска/суммы или даты периода требует нового подтверждения. Старый ключ отправки проверяется до новых данных; прежние снимки не дополняются задним числом.

[Контракт](../docs/technical/company-profile-contract.md), [фактическая проверка](../docs/technical/2026-10-24-demo-profiles-verification.md). Исполняемых проверок ФНС/БКИ, скоринга, кредитного решения и структурированного редактирования в этом этапе нет.

## Помощник через OpenAI-совместимый API

Авторизованные `GET /api/v1/assistant/status` и `POST /api/v1/assistant/chat` готовы. Модель распознаёт намерение, сервер формирует условия из каталога. Чат не меняет заявку и доступен только CLIENT для собственного DRAFT. Запуск, API, ограничения и следующий этап frontend описаны в [инструкции](../docs/technical/assistant-integration.md).
