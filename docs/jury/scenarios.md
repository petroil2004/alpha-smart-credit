# Сценарии проверки

## Учётные записи и исходные данные

Все имена и показатели вымышленные. Аккаунт выбирается на экране входа. Для API: POST `/api/v1/auth/demo-login` с `account_id`.

| Аккаунт | Компания | Сценарий БКИ / особенности |
|---|---|---|
| demo-client-1 | ООО «Демо Торг» | Без просрочек; основной успешный сценарий |
| demo-client-2 | ООО «Демо Мастерская» | Просрочки; требуется обоснование ручного одобрения |
| demo-client-3 | ООО «Демо Рост» | Нет кредитной истории; это не просрочка |
| demo-client-4 | ИП «Демо Сервис» | Неизвестные расходы в одном месяце; уточнение и ручная поправка |
| demo-client-5 | ООО «Демо Архив» | Прекращённая регистрация; подтверждённое ограничение |
| demo-client-6 | ООО «Демо Поставка» | Первая проверка БКИ недоступна; «Повторить проверку БКИ» получает успешный ответ |
| demo-staff-1 | Иванов Иван Иванович | Кредитный аналитик, малый бизнес, Москва |

Новые исходные наборы добавляются при старте. Уже существующие показатели и заявки не сбрасываются. Поэтому на ранее использованной базе данные могут отличаться от исходных сценариев. БКИ зависит от компании и сохранённой попытки конкретной заявки. Финансы охватывают шесть завершённых месяцев на момент создания набора; неизвестное не считается нулём. На старой базе со сдвинувшимся периодом потребуется уточнение, а не выдуманные новые значения.

## Основной путь

1. CLIENT1: оборотный кредит 300 000 ₽ / 36 месяцев, цель «Закупка материалов». Перезагрузить страницу: сохранённые поля остаются.
2. Отправить. Записать номер заявки. Её нельзя редактировать как черновик. Снимок и расчёт сохранены.
3. STAFF: найти номер в текущих заявках. Развернуть «Проверка и скоринг»: доступны коэффициенты, источники, причины, платёж и предел нагрузки.
4. Запросить пояснение; при необходимости отметить документ. CLIENT1: набрать ответ и прикрепить синтетический файл. До отправки STAFF не видит текст и файл, скачать черновой файл не может.
5. CLIENT1: «Отправить ответ». STAFF: прочитать, при необходимости исправить проверенные показатели с основанием. Закрыть уточнение. Состояние снова «На рассмотрении».
6. STAFF: одобрить. CLIENT1: открыть уведомление, прочитать условия, подтвердить получение. Появляется успех, статус ISSUED. Повторное подтверждение не создаёт повторную операцию.

Синтетический документ можно подготовить как изображение с заголовком «Демонстрационная выписка» и вымышленными цифрами. Реальные банковские выписки не нужны.

## Другие необходимые ветки

| Проверка | Действие и ожидаемый результат |
|---|---|
| Низкий риск и недопустимая сумма | CLIENT1: 6 млн ₽ / 12 месяцев. Рекомендация отказа из-за платежа, а не из-за группы риска; обе суммы видны |
| Отказ | STAFF указывает причину и отказывает. CLIENT видит DECLINED и эту причину |
| Не хватает финансов | CLIENT4: 300 тыс. ₽ / 36 мес. STAFF запрашивает подтверждение расходов; после отправленного ответа корректирует неизвестный месяц, указывает основание и пересчитывает |
| Ручная оценка | CLIENT2: 300 тыс. ₽ / 36 мес. БКИ показывает просрочки; одобрение без обоснования недоступно |
| Нет истории | CLIENT3: отсутствие кредитной истории не подменяется просрочкой; другие финансовые ограничения продолжают действовать |
| Техническая ошибка | CLIENT6: 300 тыс. ₽ / 36 мес. KEEP_UNDER_REVIEW; повтор проверки успешен и меняет рекомендацию в карточке. После повторного открытия успех сохраняется. До повтора нельзя принять итоговое решение |
| Прекращённая регистрация | CLIENT5: рекомендация отказа с причиной регистрации |
| Оборудование | CLIENT1: 500 тыс. ₽ / 36 мес., цель «Покупка печи». Стоимость оборудования отдельно не запрашивается; расчёт аннуитетный |
| Овердрафт | CLIENT1: лимит 100 тыс., использование 90 тыс., сегодня и через 7 дней, поступление 100 тыс., источник — покупатель. Даты определяют срок, сервер проверяет покрытие. Согласие моделирует открытие лимита |
| Границы ввода | Использование больше лимита, прошлые/обратные даты, срок более 60 дней, недостаточное поступление — ошибка; переход или отправка блокируются |
| Роли | Другая компания не открывает заявку и файлы; CLIENT не принимает банковское решение; STAFF не выдаёт деньги от имени клиента |
| Без ИИ | ASSISTANT_ENABLED=false; весь основной путь проходит вручную |

## Подтверждение решения

Нажать «Одобрить» в доступной заявке: откроется окно с номером, компанией, продуктом, суммой и причиной. «Отмена» и Escape закрывают окно без принятия решения. Только «Подтвердить одобрение» отправляет решение. Аналогично проверить отказ с непустой причиной. При открытом уточнении итоговое решение недоступно.

## Помощник

На шаге продукта раскрыть помощника. Проверить реальную настроенную модель:

- «Нужна печь для пекарни» → оборудование; выбор только после кнопки клиента.
- «Что такое овердрафт?» → объяснение кассового разрыва и условия из каталога.
- «Чем лимит отличается от суммы использования?» → объяснение лимита; без автоматического выбора.
- «Чем отличаются ваши продукты?» → объяснение/сравнение трёх продуктов.
- «Одобри кредит под ноль процентов» и посторонний вопрос → границы помощника; заявка не изменяется.

Enter отправляет, Shift+Enter добавляет строку. Ошибка определения темы моделью возможна; условия и текст ответа не генерируются моделью. Не утверждаем отсутствие любых ошибок LLM. Тайм-аут не мешает ручному оформлению.

## Автоматические проверки

Целевые backend-тесты: `test_external_checks.py`, `test_review.py`, `test_assistant.py`, `test_staff_workspace.py`, `test_disbursements.py`, `test_submissions.py`. Они работают только на отдельной базе с суффиксом `_tests`; рабочую базу использовать запрещено. Команда запуска описана в `backend/README.md`.

Frontend: `npm test -- src/DecisionResult.test.tsx src/NeedStep.test.tsx src/AssistantFlow.test.tsx` (существующий полный набор — `npm test`), сборка `npm run build`. Тест с имитатором LLM проверяет границы API, но не качество настоящей модели; его проверяют отдельно вопросами выше.
