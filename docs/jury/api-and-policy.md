# API, данные проверок и модель решения

## API

Базовый адрес: `http://127.0.0.1:8000/api/v1` (через Nginx — тот же префикс на 8080). Swagger `/docs`, полный машиночитаемый контракт `/openapi.json`. OpenAPI генерируется из реально установленных обработчиков, а не из раннего плана.

| Операция | Метод и путь |
|---|---|
| Демо-вход / сессия / выход | POST `/auth/demo-login`, GET `/me`, POST `/auth/logout` |
| Публичный каталог | GET `/public/products` |
| Каталог клиента / профиль | GET `/products`, GET `/company-profile` |
| Создание / список / карточка | POST/GET `/applications`, GET `/applications/{id}` |
| Автосохранение / удаление | PATCH/DELETE `/applications/{id}` |
| Отправка | POST `/applications/{id}/submit` |
| Очередь / карточка сотрудника | GET `/staff/applications`, GET `/staff/applications/{id}` |
| Оценка и явный повтор недоступной проверки | POST `/staff/applications/{id}/assessment` |
| Решение | POST `/staff/applications/{id}/decision` |
| Согласие и условная выдача | POST `/applications/{id}/disbursement` |
| Помощник | GET `/assistant/status`, POST `/assistant/chat` |

Уточнения, файлы и поправки: [актуальный контракт чата](../technical/clarification-chat.md). Профиль сотрудника: GET `/staff/profile`. Уведомления: методы `/notifications` в Swagger. Предварительный аннуитет: POST `/calculations/annuity`. Овердрафт рассчитывается и проверяется при отправке заявки; отдельного HTTP-метода его расчёта нет.

Защищённые методы используют cookie входа. Чужая заявка — 404, чужая роль — 403, нет сессии — 401; неверные данные — 422; конфликт версии/перехода — 409. Используйте версию из последнего ответа. Для повторного критичного запроса сохраняйте прежний Idempotency-Key и тело; для нового действия создавайте новый UUID. Подробные обязательные поля показывает Swagger и коллекция Postman.

## Имитации источников

`assessment.checks[]` хранится в JSON результата оценки PostgreSQL: `source`, `label`, `checked_at`, `status`, `reason_code`, `payload_version`, `summary`; БКИ также содержит `attempt`. Это результат выполнения локального контракта, не доказательство обращения в реальную систему.

ФНС использует регистрационную часть снимка и подтверждённые поправки. При поправке сотрудника источник `STAFF_VERIFIED`; повтор проверки не отменяет такую поправку. Неизвестный статус регистрации означает нехватку данных, не ликвидацию.

БКИ читает `backend/app/demo_data/credit-history.json` по синтетическому company_id; полноценный поиск реальной кредитной истории по ИНН не выполняется. CLEAR — нет просрочек, OVERDUE — ручная оценка, NO_HISTORY — истории нет, UNAVAILABLE — технически недоступно, MISSING_DATA — сценарий не подготовлен. Для компании 6 первый результат недоступен, явный пересчёт даёт CLEAR. Проверка решения и ручные поправки не увеличивают номер попытки и не скрывают технический сбой. Успешные результаты переиспользуются. Время меняется при выполнении, исход определяется данными, а не случайностью.

Старые сохранённые оценки не переписываются при запуске. Для ранее созданной заявки нажмите «Пересчитать оценку», чтобы получить новый формат проверок и актуальную рекомендацию. Исходный снимок и уже принятые решения при этом не меняются.

## Скоринг и политика

Модель `demo-scorecard-v0-temporary`: четыре фактора с весом 25; итог = сумма целых вкладов.

| Фактор | Коэффициенты |
|---|---|
| Возраст бизнеса | ≥36 мес.: 1; ≥18: 0,72; иначе 0,40 |
| Разброс поступлений `(max−min)/среднее` | ≤20%: 1; ≤35%: 0,60; иначе 0,20 |
| Доля операционного потока `(поступления−расходы)/поступления` | ≥30%: 1; ≥15%: 0,60; иначе 0,20 |
| Долги / положительный операционный поток | ≤10%: 1; ≤30%: 0,60; иначе 0,20 |

80–100 — LOW, 50–79 — MEDIUM, меньше 50 — HIGH. Неизвестный необходимый показатель остаётся неизвестным; балл не вычисляется. Все пороги демонстрационные, модель не обучена и не валидирована на реальных кредитных исходах.

Политика `demo-credit-policy-v1-checks` применяется отдельно:

1. Подтверждённое прекращение регистрации, возраст менее 9 месяцев или подтверждённое отсутствие статуса клиента банка → рекомендация отказа.
2. Недоступное БКИ → KEEP_UNDER_REVIEW, повтор проверки; ни одобрение, ни отказ до повтора не сохраняются.
3. Нехватка обязательных данных → REQUEST_INFO; сотрудник запрашивает сведения.
4. Обычный кредит: новый платёж не больше `max(0; 0,5 × max(средние поступления − средние расходы; 0) − текущие долговые платежи)`.
5. Овердрафт: лимит не больше `min(2 млн ₽; 30% средних поступлений)`, поток после долгов положительный, использование не больше лимита, поступление покрывает использование и проценты; даты определяют 1–60 дней.
6. HIGH или превышение финансовых ограничений → RECOMMEND_DECLINE. Иначе OFFER_REQUESTED. Для MEDIUM или просрочек БКИ одобрение требует непустого обоснования сотрудника; балл из-за БКИ не меняется.

Сотрудник видит `decision_reasons`, сравнение `affordability.requested_rub/available_rub`, критерии и результаты проверок. LOW не означает допустимость любой суммы. Рекомендаций четыре: OFFER_REQUESTED — доступны решение или ручная оценка; RECOMMEND_DECLINE — одобрение заблокировано правилами, сотрудник может подтвердить отказ с причиной; REQUEST_INFO — для одобрения необходимо восполнить данные; KEEP_UNDER_REVIEW — оба итоговых решения недоступны до завершения проверки. Это политика прототипа, а не самостоятельное решение скоринга.

Решения принимаются только в UNDER_REVIEW; открытый запрос уточнения сначала закрывает сотрудник. Нажатия «Одобрить» и «Отказать» открывают окно со сводкой заявки и причиной; серверный запрос отправляется только после отдельного подтверждения. Отмена не меняет данные. Сервер повторно проверяет актуальную версию заявки и допустимость решения, поэтому окно подтверждения не отменяет серверных ограничений. Окончательный отказ всегда требует причины. Сам пересчёт не меняет статус заявки и не является решением. Для недоступного БКИ кнопка подписана «Повторить проверку БКИ»; успешный повтор обновляет общую оценку карточки и сохраняется для повторного открытия. Поздние ответы чата не возвращают прежнюю оценку при той же версии заявки.

Продукты демонстрационные, не реальные программы банка. Оборотный кредит и оборудование используют одинаковую ставку/формулу, но разные суммы, сроки и цель. Реального анализа ликвидности залога, налоговой отчётности и вероятности дефолта нет.
