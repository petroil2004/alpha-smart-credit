# Первый этап: каталог и калькулятор обычных кредитов

Версия контракта от 23.10.2026. Детализирует согласованный объём из [общей спецификации](../superpowers/specs/2026-10-23-credit-policy-alignment-design.md) после утверждения плана Петей. Описанные методы реализованы в ветке калькулятора. Условия взяты из [каталога Киры](../business/product-catalog.md); действующий [API черновиков](api-contract.md) сохраняется.

## Результат этапа

Клиент после входа открывает черновик, выбирает оборотный кредит или кредит на оборудование, задаёт сумму и срок ползунками либо вручную и видит рассчитанные сервером ставку, ежемесячный платёж, общую сумму выплат и переплату. На шаге проверки отображается тот же актуальный расчёт. Кнопка «Сохранить черновик» работает отдельно.

Каталог содержит все три продукта. На этом этапе аннуитетный расчёт доступен только для двух обычных кредитов; поля и сохранение овердрафта продолжают работать, но аннуитет к нему не применяется. Профиль, дополнительные поля, финансовая анкета, предварительная оценка доступности, скоринг, отправка, решение сотрудника и LLM не входят в этот этап. Платёж не означает одобрения.

## Подход

Добавляем два метода в существующий FastAPI backend. Каталог и расчёт не читают/не меняют заявки и не требуют миграции БД. Клиент отправляет текущий ввод без неявного сохранения. Ставки и пределы заданы в одной серверной конфигурации; frontend не копирует их в константы. Для чисел UI-ползунков допустимы безопасные целые значения, но денежный ввод, отображение и запросы сохраняют копейки.

Альтернативы: отдельная кнопка «Рассчитать» сокращает запросы, но неудобна при движении ползунка; расчёт в браузере создаёт второй источник формул. Выбран пересчёт сервером после паузы 300 мс с защитой от устаревших результатов. Существующий транспорт сохраняет таймаут 15 секунд.

## GET /api/v1/products

Требует существующую cookie-сессию; без неё 401 UNAUTHENTICATED. Ответ 200: объект `catalog_version: string` и `items: Product[]` в порядке working_capital, equipment, overdraft. Начальная версия — `2026-10-23.1`; она описывает демонстрационные параметры, а не текущую дату запроса.

| Поле Product | Тип | Значение / смысл |
| --- | --- | --- |
| code | string | working_capital / equipment / overdraft |
| title | string | Название из действующих карточек |
| description | string | Краткое назначение продукта |
| annual_rate_percent | decimal string | 25.00 / 25.00 / 26.00; это проценты годовых, не доля единицы |
| amount_min_rub | decimal string | 300000.00 / 500000.00 / 50000.00 |
| amount_max_rub | decimal string | 6000000.00 / 10000000.00 / 2000000.00 |
| amount_step_rub | decimal string | 10000.00; шаг ползунка, не ограничение ручного ввода |
| term_min_months | integer or null | 12 / 12 / null |
| term_max_months | integer or null | 36 / 60 / null; шаг ползунка срока — 1 месяц |
| limit_term_months | integer or null | null / null / 12 |
| usage_min_days | integer or null | null / null / 1 |
| usage_max_days | integer or null | null / null / 60 |
| calculation_kind | string | annuity / annuity / overdraft |
| calculation_available | boolean | true / true / false в рамках этого этапа |

Карточки выбора могут дополняться полученными диапазонами и ставками. Существующие frontend-подписи остаются запасным отображением названий при недоступном каталоге, без выдуманных ставок и расчётов. Это не второй источник финансовых параметров.

## POST /api/v1/calculations/annuity

Требует cookie-сессию. Тело строго содержит три поля; лишние запрещены, в том числе присланная ставка, клиентский платёж или application_id.

```json
{"product_code":"working_capital","amount_rub":"3000000.00","term_months":36}
```

`product_code` — только working_capital или equipment. `amount_rub` — положительная десятичная строка без знака, экспоненты, запятых и пробелов, не более двух дробных знаков, внутри диапазона продукта. Значения `3000000` и `3000000.0` допустимы и нормализуются. `term_months` — строго целое JSON-число внутри диапазона; bool, строка и дробное число не принимаются. UI использует существующую нормализацию пробелов и запятой до запроса. Продуктовые ограничения относятся к расчёту; PATCH черновика по-прежнему допускает сохранение суммы вне каталога и неполных параметров в технических пределах.

Ответ 200:

```json
{
  "catalog_version":"2026-10-23.1",
  "product_code":"working_capital",
  "amount_rub":"3000000.00",
  "term_months":36,
  "annual_rate_percent":"25.00",
  "monthly_payment_rub":"119279.48",
  "total_payment_rub":"4294061.28",
  "overpayment_rub":"1294061.28"
}
```

Все денежные поля и ставка — строки, срок — число. Сервер использует Decimal с локальной точностью не менее 40 значащих цифр: `r = annual_rate_percent / 100 / 12`; `A = S × r / (1 − (1+r)^(-n))`; при r=0 — S/n. Промежуточные значения не округляются. Платёж округляется до копеек по ROUND_HALF_UP; итог = округлённый платёж × месяцы; переплата = итог − сумма. Полный график с корректировкой последнего платежа не строится. Нулевую ставку проверяем для чистой функции, не добавляя такой продукт в каталог.

Второй эталон: equipment, 5000000.00, 45 месяцев → платёж 172289.03, итог 7753006.35, переплата 2753006.35. Граничные суммы проходят включительно; ручной ввод 300000.01 также допустим, независимо от шага ползунка.

Ошибки используют существующую оболочку `{error:{code,message,fields?}}`: 401 UNAUTHENTICATED, 422 VALIDATION_ERROR с product_code/amount_rub/term_months, 500 SERVER_ERROR. Некорректный ввод не изменяет заявку. Клиентский текст бизнес-ошибки: «Для расчёта укажите сумму от {min} до {max} ₽» / «Для расчёта укажите срок от {min} до {max} месяцев». Для запроса овердрафта указать, что аннуитетный расчёт к нему неприменим.

## Поведение интерфейса

- На шаге «Потребность» сохраняется существующая сумма. На «Параметрах» обычного кредита показываем эту же сумму и срок с ползунками и ручным вводом. Это общие значения черновика, без отдельной копии состояния калькулятора. Под каждым контролом виден диапазон каталога.
- Переключение продукта не подгоняет сумму или срок автоматически. Если значение не подходит новому диапазону, показывается подсказка, расчёта нет; пользователь решает, что исправить. Сохранение неполного черновика остаётся доступным.
- Шаг суммы ползунка — 10000 ₽, срока — месяц. Ручной ввод с копейками сохраняется точно. При загрузке значения не округляются и не заменяются положением ползунка: для недопустимого/неполного значения ползунок только отображает безопасную позицию и изменяет ввод лишь при явном действии пользователя. Пустые поля не заполняются молча.
- Блок результата называется «Предварительный расчёт платежа». Под ним: «Демонстрационные условия. Без комиссий и дополнительных платных услуг. Расчёт не означает одобрения кредита. Итог рассчитан как равный платёж × число месяцев; полный график не строится».
- При корректных параметрах и загруженном каталоге запрос идёт через 300 мс после последнего изменения; таймер сбрасывается при новом вводе. Результат скрывается сразу при изменении расчётных параметров, включая момент до запуска нового запроса.
- Ключ результата включает id черновика, продукт, нормализованную сумму, срок и версию каталога. Показывается только ответ текущего ключа и последнего запроса. Поздний ответ, включая позднюю ошибку, не заменяет новый результат. Уход из черновика/аккаунта отключает применение его ответов. Версия ответа должна совпасть с каталогом; иначе результат скрывается и предлагается обновить каталог. Продукт, нормализованная сумма и срок ответа должны совпадать с запросом, ставка — с каталогом, денежные результаты — быть строками до копеек. Несогласованный или неполный ответ отображается как ошибка сервиса, не как расчёт для текущих параметров.
- Ввод с незаполненными/некорректными параметрами не вызывает запрос. Отсутствие результата, ожидание, ошибка параметров и недоступность сервиса имеют отдельные состояния. Ошибки калькулятора не становятся запретом сохранения черновика и не переписывают сообщения об ошибках сохранения.
- Неудача загрузки каталога оставляет существующий ручной ввод и сохранение; показываются сообщение и «Повторить загрузку условий». Ошибка расчёта скрывает прежние суммы, сохраняет ввод и предлагает «Повторить расчёт». 401 требует повторного входа без молчаливого удаления ввода. Не подставлять браузерный расчёт вместо серверного.
- Ожидание расчёта не блокирует навигацию и сохранение. Во время сохранения или смены аккаунта действующая блокировка формы применяется и к ползункам. Enter внутри полей сохраняет прежнюю семантику перехода/сохранения; кнопки повтора имеют type=button.
- На шаге «Проверка» показывается тот же актуальный результат либо его состояние, без отдельного запроса и без новых редактируемых значений. При овердрафте сохраняются нынешние поля, а аннуитетный блок скрыт; можно показать «Калькулятор овердрафта пока недоступен».

## Проверка готовности

Проверки backend: два эталонных расчёта, копейки и округление, границы продуктов, неверные типы и лишние поля, авторизация, неизменность заявки/версии после расчёта. Проверки frontend: связь ползунков и ввода, общая сумма между шагами, пустые/старые значения без автоподмены, задержка запросов, обратный порядок ответов, сбои и смена черновика/продукта, сохранение во время расчёта, сводка. Старые проверки черновиков продолжают проходить.

Финальная ручная проверка — действующий backend и PostgreSQL: вход → черновик → сумма/срок → серверный расчёт → явное сохранение → перезагрузка → тот же ввод и повторный расчёт. Использовать отдельный тестовый черновик. Автотесты backend запускаются только на отдельной тестовой БД: существующие проверки удаляют схему указанной DATABASE_URL базы. Не удалять рабочий Docker volume и сохранённые пользователем черновики.
