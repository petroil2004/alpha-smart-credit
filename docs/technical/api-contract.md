# Контракт первого шага: черновик заявки

Реализованный [каталог и калькулятор обычных кредитов](loan-calculator-contract.md) дополняют API отдельными авторизованными методами. Сохранение черновика из этого документа не меняется; продуктовые пределы расчёта не становятся запретом сохранения неполного черновика.

Версия 1.0, 21 октября 2026 года. Общая техническая договорённость Пети и Виктора для параллельной реализации. Она не задаёт окончательные условия кредитования и не заменяет материалы Насти, Саши и Киры. Любое изменение этого обмена согласуется между Петей и Виктором до реализации.

Бизнес-правила уточнены 23.10.2026: [каталог](../business/product-catalog.md), [поля и обязательность](../business/application-fields.md), [решения](../business/decision-rules.md), [сводная спецификация](../superpowers/specs/2026-10-23-credit-policy-alignment-design.md). Профиль, категория цели, поля оборудования и план оплаты овердрафта, финансовые сведения, оценка доступности и отправка ещё требуют технического контракта и реализации. Каталог и расчёт платежа обычных кредитов добавлены отдельными методами по ссылке выше. Существующие редактируемые поля сохраняют имена, денежные строки допускают копейки, неполный черновик по-прежнему можно сохранить.

## Результат шага

Клиент входит в демонстрационный профиль, создаёт черновик, изменяет его, сохраняет и повторно открывает после обновления страницы. Хранение выполняется сервером. В этой версии нет отправки на рассмотрение, скоринга, кредитного решения, ставок и реальной выдачи. Модель для этого шага не требуется.

## Разделение файлов

- Петя: `frontend/`, этот контракт, документация frontend, корневые README и AGENTS при необходимости.
- Виктор: `backend/`, `backend/README.md`, `compose.yaml`, корневая `.env.example` для backend/БД. Не добавляет свой frontend и не меняет контракт в одиночку.
- Каждый использует собственную ветку от main и свою локальную копию. Нельзя копировать весь frontend или backend другого человека ради объединения: используем PR.

## Адрес и вход

Базовый путь `/api/v1`. Backend запускается на `127.0.0.1:8000`. Frontend Vite на `127.0.0.1:5173` перенаправляет `/api` к backend. Адрес перенаправления задаётся настройкой `VITE_API_PROXY_TARGET`; по умолчанию `http://127.0.0.1:8000`. Браузер использует относительные адреса и cookie через тот же сайт; для разработки не нужен открытый CORS на все сайты.

Демонстрационный вход не выдаём за промышленную авторизацию. Сервер разрешает только известные тестовые аккаунты и устанавливает HttpOnly-cookie сессии. Компания и роль берутся из серверной сессии, а не из полей тела запроса, заголовков роли или localStorage. Сессия и черновики должны переживать перезапуск приложения при сохранённой БД/настройках.

Тестовые аккаунты `demo-client-1` и `demo-client-2` принадлежат разным компаниям. Первый: `user.id = demo-client-1`, `company.id = demo-company-1`, название компании `ООО «Демо Торг»`; второй: `demo-client-2`, `demo-company-2`, `ООО «Демо Мастерская»`. Имена пользователей демонстрационные. Они нужны для проверки изоляции данных. Банковскую роль добавляем следующими шагами.

## Запросы

| Метод и путь | Тело запроса | Успешный ответ |
|---|---|---|
| GET `/health` | — | 200 `{"status":"ok"}`; без входа |
| POST `/auth/demo-login` | `{"account_id":"demo-client-1"}` | 200: текущий пользователь и компания; устанавливает cookie |
| GET `/me` | — | 200: тот же объект; 401 без сессии |
| POST `/auth/logout` | — | 204; удаляет сессию/cookie |
| GET `/applications` | — | 200 `{"items":[Application]}`, только свои; новые изменения сверху |
| POST `/applications` | `{}` | 201: новый пустой Application; обязательный `Idempotency-Key` |
| GET `/applications/{id}` | — | 200: свой Application; 404 для отсутствующего или чужого |
| PATCH `/applications/{id}` | Изменяемые поля плюс обязательный `version` | 200: обновлённый Application; только свой DRAFT |

Ответ `/me` и входа:

```json
{
  "user": {"id":"demo-client-1","name":"Демо-клиент 1","role":"CLIENT"},
  "company": {"id":"demo-company-1","name":"ООО «Демо Торг»"}
}
```

Любой `/applications` требует сессию; `company_id`, `id`, `status`, время и версию назначает сервер. Если клиент пытается изменить серверные поля, сервер отклоняет запрос, а не доверяет им.

## Application

```json
{
  "id":"00000000-0000-4000-8000-000000000001",
  "company_id":"demo-company-1",
  "status":"DRAFT",
  "purpose":null,
  "product_code":null,
  "amount_rub":null,
  "term_months":null,
  "usage_days":null,
  "expected_inflow_date":null,
  "expected_inflow_amount_rub":null,
  "version":1,
  "created_at":"2026-10-21T17:00:00Z",
  "updated_at":"2026-10-21T17:00:00Z"
}
```

Это полный пример формы ответа, а не фиксированные id и даты. id — UUID-строка; время — ISO 8601 UTC. Все перечисленные поля ответа присутствуют, неизвестные значения равны null.

Редактируемые поля:

| Поле | Вид и проверка первого шага |
|---|---|
| `purpose` | Текст до 500 символов; пробелы по краям удаляются; пустое — null |
| `product_code` | `working_capital`, `equipment`, `overdraft` либо null |
| `amount_rub` | Строка с положительной суммой, максимум 2 знака после точки, либо null; ответ нормализован до 2 знаков |
| `term_months` | Положительное целое либо null; применимо только к обычным кредитам |
| `usage_days` | Положительное целое либо null; только для овердрафта |
| `expected_inflow_date` | Корректная дата YYYY-MM-DD либо null; для овердрафта |
| `expected_inflow_amount_rub` | Положительная денежная строка либо null; для овердрафта |

На уровне черновика разрешены неполные сведения и даты в прошлом: окончательная проверка достаточности и условий будет перед отправкой после согласования бизнес-правил. Запрещены неверные типы, некорректные даты, отрицательные значения, неизвестные коды продукта и дробные месяцы/дни. Никаких вымышленных кредитных лимитов, ставок и порогов скоринга.

Для `product_code = null` параметры обоих видов срока и ожидаемого поступления равны null; при обычном продукте поля овердрафта null; при овердрафте `term_months` null. При смене продукта frontend явно сбрасывает неприменимые поля, backend проверяет итоговое сочетание. Денежные строки API используют точку; UI может принимать пробелы и запятую и приводит их к формату API без потери копеек.

PATCH может содержать часть полей; переданное null очищает значение. `version` — версия последнего прочитанного объекта. Сервер атомарно проверяет совпадение; при успехе увеличивает version на 1. При несовпадении — 409, без перезаписи чужих изменений. Даже сохранение без изменения полей может увеличить version: frontend использует возвращённую сервером.

POST принимает только пустое тело `{}`. `Idempotency-Key` — UUID, создаваемый frontend один раз на попытку создания и сохраняемый до успешного ответа. Повтор с тем же ключом и тем же пользователем возвращает тот же черновик (200 или 201), не создавая второй. Ключи разных пользователей независимы. PATCH не создаёт новых объектов, защита повторного сохранения обеспечивается version. Ключи создания сохраняются на стороне backend, включая перезапуск.

## Ошибки

```json
{"error":{"code":"VALIDATION_ERROR","message":"Проверьте заполнение полей","fields":{"amount_rub":"Укажите положительную сумму"}}}
```

`fields` необязателен. Коды: 401 `UNAUTHENTICATED`; 404 `NOT_FOUND`; 409 `VERSION_CONFLICT`; 422 `VALIDATION_ERROR`. Неизвестный тестовый аккаунт — 422. Ошибка сервера — 500 с общим сообщением, без трассировки и секретов. Детали `fields` используют имена редактируемых полей из контракта.

Frontend обрабатывает также не-JSON ответ и недоступный backend: сохраняет введённый текст, сообщает о проблеме и предлагает повторить. При 409 не перезаписывает изменения автоматически: можно явно загрузить сохранённую версию после предупреждения о замене ввода. При 401 показывает необходимость входа, не очищая редактируемый черновик без предупреждения. Выход и смена компании очищают данные прежней компании в интерфейсе.

## Приёмка совместной версии

1. Вход → пустой список → создание → редактирование → сохранение → обновление страницы → сохранённые значения.
2. Остановка и запуск backend с той же БД: данные и сессия сохраняются.
3. Второй тестовый клиент не видит и не читает заявку первого.
4. Повтор создания с одним ключом даёт одну заявку.
5. Два окна: второе сохраняет старую версию и получает 409 без потери своего ввода.
6. Сбой сохранения не очищает поля и не показывает ложный успех.
7. Смена продукта не оставляет несовместимые поля.

Frontend временно можно проверять с тестовым сервером, повторяющим этот контракт. В рабочем режиме нельзя незаметно заменять недоступный backend сохранением в браузере. Пока backend Виктора не проверен вместе с frontend, результат называется «интерфейс с проверкой по контракту», а не завершённая серверная интеграция.

## Клиентское автосохранение (23.10.2026)

Формат API не изменился. Frontend отправляет частичные PATCH через 1500 мс после паузы и при переходе шага, последовательно с последней подтверждённой version. Невалидные промежуточные поля исключаются, зависимые поля при смене продукта группируются; ответ не заменяет новый ввод. При 401/409 автоматические повторы останавливаются. «Сохранить и выйти» завершает очередь и открывает список, не подаёт заявку в банк. Подробности — в [дизайне](../superpowers/specs/2026-10-23-autosave-design.md).
