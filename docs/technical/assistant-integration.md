# Подключение помощника через Ollama

## Состояние

Основной кредитный MVP объединён в main через PR №12. Backend помощника реализован отдельно: `GET /api/v1/assistant/status` и `POST /api/v1/assistant/chat`. По умолчанию выключен. Клиентский блок `AssistantPreview` пока остаётся заготовкой: чат в интерфейсе ещё не подключён. Реальная модель на компьютере Пети не установлена; качество ответов и скорость CPU пока не проверены. Платных API нет.

## Как устроен первый вариант

Клиент описывает задачу → backend проверяет сессию, принадлежность заявки и DRAFT → Ollama распознаёт намерение/продукт → сервер проверяет JSON → формирует русский ответ из актуального каталога → интерфейс показывает ответ и необязательную кнопку выбора продукта.

Модель не пишет пользовательский ответ напрямую: она выбирает `recommend`, `compare`, `terms`, `clarify` или `unsupported` и один из трёх product_code/null. В первой версии это ограниченный помощник по выбору, с подготовленными сервером формулировками. Это исключает придуманные ставки, проценты, пороги скоринга и обещания одобрения. Расчёты остаются в `calculator.py`, скоринг в `review.py`, решения — у сотрудника.

В модель передаются только системная инструкция, код выбранного продукта и ограниченная история разговора. Backend не добавляет компанию/ИНН, банковские финансы, баллы, документы или другие заявки. Пользовательский текст не считается командой на изменение системы. История не сохраняется в БД; дополнительных таблиц и миграций нет. На старте frontend хранит её только в памяти текущего черновика и очищает при смене заявки/профиля.

## Контракт для frontend

Оба метода требуют CLIENT-сессию. STAFF403, без входа401. Status возвращает `{enabled, available, model, reason}`; причины `DISABLED`, `MODEL_MISSING`, `UNAVAILABLE`. Проверять status при раскрытии блока, а не постоянным опросом.

POST chat:

```json
{
  "application_id": "00000000-0000-4000-8000-000000000001",
  "message": "Хочу купить печь для пекарни",
  "history": [{"role": "user", "content": "У меня пекарня"}]
}
```

UUID должен принадлежать собственному черновику. Сообщение до1200 символов, до6 предыдущих сообщений user/assistant, суммарно до4000 символов; пустые сообщения и лишние поля отклоняются. System-роль клиента запрещена. Ответ:

```json
{
  "answer": "Для покупки оборудования можно рассмотреть этот вариант. …",
  "suggested_product": "equipment",
  "products": [],
  "catalog_version": "2026-10-23.1",
  "source": "SERVER_CATALOG",
  "model": "qwen2.5:1.5b",
  "disclaimer": "Демонстрационные условия. …"
}
```

`products` в реальном ответе содержит соответствующие полные строки прежнего `/products` (для сравнения все3); здесь массив сокращён для примера. `suggested_product` бывает null. Не подставлять его автоматически: кнопка «Выбрать этот продукт» должна вызывать прежний обработчик смены продукта, очищающий неприменимые поля и сбрасывающий подтверждение. Никакого отдельного пути создания/отправки через ИИ.

Чужая заявка404, отправленная409 `ASSISTANT_DRAFT_ONLY`, неверные поля422, занятая модель429 `ASSISTANT_BUSY`. Отключение/ошибка/повреждённый ответ модели503 с кодом `ASSISTANT_DISABLED`, `ASSISTANT_UNAVAILABLE`, `ASSISTANT_MODEL_MISSING` или `ASSISTANT_BAD_RESPONSE`. Интерфейс показывает спокойное сообщение и кнопку повтора, оставляя ручной выбор и «Продолжить» доступными. Не повторять POST автоматически бесконечно. Незавершённый или невалидный ответ модели не выдаётся как совет.

## Воспроизводимый CPU-запуск

По умолчанию `docker compose up` запускает только прежние db/backend. Ollama включается профилем `assistant`, не публикует порт на хост/интернет, модели лежат в отдельном volume. CPU2, память до3ГиБ, одна модель/один запрос одновременно. Существующую БД не удалять и `down -v` не выполнять.

Для имеющегося локального проекта (если у Виктора другое имя Compose-проекта, использовать его):

```bash
# В корне проекта. Запускает только необязательный сервис, без второй БД.
docker compose -p alpha-credit-pr3 --profile assistant up -d ollama

# Однократная загрузка весов в volume, интернет нужен только для скачивания.
docker compose -p alpha-credit-pr3 exec ollama ollama pull qwen2.5:1.5b

# Включить помощника в существующем backend.
ASSISTANT_ENABLED=true docker compose -p alpha-credit-pr3 up -d --build --no-deps backend
```

Для постоянного включения задать `ASSISTANT_ENABLED=true` в локальном `.env` (не коммитить). Остальные настройки есть в `.env.example`: адрес `http://ollama:11434`, модель `qwen2.5:1.5b`, тайм-аут90сек. При обычном следующем запуске без этого флага/.env помощник снова выключен. Чтобы отключить: задать false и пересоздать только backend; Ollama можно остановить командой `docker compose -p alpha-credit-pr3 --profile assistant stop ollama`, сохранив веса.

Qwen2.5 1.5B выбран для дешёвого распознавания короткой русской задачи на CPU; вес файла около986МБ, Apache2.0 по [карточке модели](https://ollama.com/library/qwen2.5:1.5b). Скорость/точность зависят от компьютера. При недостаточной точности заменить `OLLAMA_MODEL` и повторить несколько ручных сценариев; сначала оценить текущую модель, не добавлять RAG/векторную БД для трёх продуктов. Размер image Ollama скачивается дополнительно. Образ `ollama/ollama:latest` после первого успешного запуска желательно закрепить digest; сейчас версия не зафиксирована.

Используется официальный [POST /api/chat](https://docs.ollama.com/api/chat): JSON schema в format, stream=false, num_predict128, num_ctx4096, temperature0. Объём HTTP-ответа ограничен64КиБ. Запросов к платному API или автоматических загрузок модели из backend нет. Docker-вариант соответствует [официальному CPU-запуску](https://docs.ollama.com/docker), но без внешнего порта.

## Что делаем следующим шагом

1. Запустить Ollama и скачать модель, проверить available=true под клиентской сессией.
2. Подключить существующий `AssistantPreview`: поле сообщения, список ответов, состояние ожидания, повтор и status; добавить типы и2 метода к существующему API-клиенту.
3. Показать карточку рекомендованного продукта и кнопку явного выбора. На других шагах и после отправки помощника не показывать.
4. Проверить коротко: товар→оборотный, печь→оборудование, оплата до поступления→овердрафт, неясная задача→вопрос; сравнение/условия; запрос «одобри под0%»; недоступная модель; смена заявки/компании во время ожидания. Поздний ответ не должен менять новый экран.
5. Замерить время первого и повторного ответа на компьютере Виктора, поправить инструкцию классификатора по реальным ошибкам. Только после этого расширять свободный диалог. При необходимости более свободного текста потребуются дополнительные проверки фактических утверждений.

## Выполненные проверки

Четыре новых backend-теста: права/отключение/отправленный черновик, реальный HTTP к имитатору Ollama и ответ из каталога без изменения заявки, тайм-аут и освобождение слота, ограничения входа/перегрузка. Чужой продукт и лишнее поле с «одобрением под0%» отклоняются. Это проверка интеграционного кода с имитатором, а не успешный запуск настоящей LLM.

Полный backend-набор после добавления помощника:170 passed на отдельной PostgreSQL `credit_cabinet_submit_tests`. Frontend не менялся относительно проверенных208 тестов и успешной сборки PR №12. Compose config подтвердил db/backend по умолчанию и дополнительный Ollama без published ports только с профилем assistant.

На действующем сервере после обновления проверены status с DISABLED и chat с503 ASSISTANT_DISABLED. Черновик до/после запроса совпал. Сервис Ollama и веса не запускались/не скачивались, основная БД не очищалась.
