# Витя: серверная часть, Ollama и воспроизводимый запуск

**Актуализация 23.10.2026.** Условия и пороги больше не нужно придумывать заново: реализуй согласованные правила. Перед расширением существующего API фиксируем новый контракт с Петей; сохраняем денежные строки с копейками и работу неполных черновиков. Точное распределение следующей кодовой задачи ещё обсуждается. Общая [спецификация согласования](../superpowers/specs/2026-10-23-credit-policy-alignment-design.md), [каталог](../business/product-catalog.md), [поля](../business/application-fields.md), [правила решений](../business/decision-rules.md) имеют приоритет над первоначальными формулировками задания ниже. Их нужно передавать LLM вместе с материалами своей задачи.

## Зачем нужна твоя работа

Сделать сервер, который хранит заявку, проверяет данные и права, выполняет согласованные расчёты и действия, а также подключает ассистента. Работа ведётся через твой Codex. Ты не должен самостоятельно изобретать банковские правила: их готовят Настя, Саша и Кира.

Сначала прочитай [общие договорённости](../superpowers/specs/2026-10-21-credit-cabinet-design.md). Серверная часть — единое приложение FastAPI; данные — PostgreSQL; запуск — Docker Compose; модель — через Ollama. Backend означает серверную часть, frontend — сайт, с которым работает человек.

## Как работать в репозитории

Прочитай [пошаговую Git-инструкцию](06-git-workflow.md). Получи существующий репозиторий команды с историей и общей документацией. Для каждой задачи — новая ветка от свежей main: сначала, например, `codex/vitya-application-api`, отдельно для подключения модели — `codex/vitya-ollama`. Не работай в main и не держи одну серверную ветку все шесть дней.

Примеры коммитов: `feat(api): добавить отправку заявки`, `fix(applications): запретить повторную выдачу`, `build(docker): добавить CPU-запуск Ollama`. Выбирай только относящиеся к задаче файлы; в PR укажи проверки и изменения обмена с сайтом. Петя проверяет твой код; Настя, Саша и Кира проверяют свои правила. После проверки вы с Петей объединяете через обычный merge, сохраняя коммиты. Не применяй force push и не меняй договорённости API без Пети.

Помоги аналитикам при конфликтах; смысл исправленного документа подтверждает его владелец. Веса модели, реальные `.env`, локальные базы и ZIP с копиями документов не загружай. Перед сдачей совместно с Петей проверь конкретный коммит main и инструкцию запуска этой версии.

## Входные материалы

| От кого | Что получить |
|---|---|
| Настя | Словарь полей, правила обработки и шесть синтетических историй |
| Саша | Расчёт баллов, причины и проверочные примеры |
| Кира | Каталог, формулы, таблица решений и правила альтернатив |
| Петя | Согласованные действия экранов и обмен с сервером |

В первый день можно строить хранение и путь на явно временных данных. Финальную кредитную логику подключать только к одной согласованной версии материалов.

## Что сделать по шагам

### День 1: договориться и проверить модель отдельно

1. С Петей зафиксировать поля и действия API. Занести их в один документ проекта; подготовить OpenAPI — машиночитаемое описание запросов и ответов, из которого FastAPI показывает Swagger, страницу для их проверки.
2. Через Codex выделить небольшие модули: пользователи и права, данные и проверки, расчёты, скоринг, решения, заявки и история, оформление, ассистент. Не строить отдельный сервис для каждого модуля.
3. С Петей проверить локальную Ollama и модель `qwen3:4b-instruct-2507-q4_K_M`. Сохранить точный идентификатор модели и версию Ollama. Начать с коротких русских ответов и ограниченного контекста.
4. Проверить OpenAI-совместимый `/v1/chat/completions`. Предусмотреть настройки `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. Это предлагаемые единые имена настроек проекта; они не означают обязательный платный API. Локальная Ollama не требует действительного облачного ключа.

После установки Ollama первая ручная проверка на компьютере Пети: скачать модель командой `ollama pull qwen3:4b-instruct-2507-q4_K_M`, открыть разговор командой `ollama run qwen3:4b-instruct-2507-q4_K_M` и задать несколько русских вопросов. `ollama ps` показывает, использует ли запущенная модель процессор или видеокарту. В Docker команды и адреса будут другими; их создаёт и проверяет Codex для выбранного способа запуска. Эти команды приведены как инструкция будущей работы: при подготовке ТЗ модель не устанавливалась и не запускалась.

### День 2: минимальный полный процесс

Реализовать тестовый вход и проверку прав, сохранение черновика, отправку, очередь сотрудника, предложение, принятие, условное подписание и моделируемую выдачу обычного кредита. Все изменения — через сервер; история и данные сохраняются в БД. Входные данные клиента нельзя принимать как подтверждение его роли.

### День 3: реальные для MVP правила и овердрафт

1. Подключить материалы Насти, Саши и Киры. Проверить их примеры автоматическими проверками, сгенерированными Codex. Начинать с проверки ожидаемого поведения, затем реализации.
2. Считать деньги точно до копеек. Готовые условия возвращать сайту, а не доверять суммам, присланным из браузера.
3. Разделить оценку риска и решение. Сохранять использованные данные и версии правил, чтобы объяснить результат.
4. Проверять альтернативу теми же ограничениями, что первоначальный запрос. Ограничить поиск допустимыми суммами и сроками из каталога; не допускать бесконечного перебора.
5. Реализовать отдельные лимит и использование овердрафта. Только одна моделируемая оплата; превышение доступного лимита запрещено.

### День 4: уточнения и полноценное подключение ассистента

1. Запрос сотрудника, ответ клиента и вложение остаются в существующей заявке. В открытом запросе `NEEDS_INFO` клиент может задать сотруднику вопрос и получить ответ; сервер проверяет автора и доступ к этой заявке. Эти сообщения сохраняются, но не меняют статус. Только явная отправка уточнения с данными/документами возвращает заявку на рассмотрение и запускает повторную оценку. Изменение исходных сведений не оставляет действующим старое предложение. Отдельного свободного мессенджера нет.
2. Вложения хранить в постоянном каталоге, с владельцем и заявкой в БД. Для MVP достаточно PDF и TXT до 5 МиБ каждый; содержимое не распознавать и не передавать автоматически модели. Разрешение на скачивание проверять на сервере.
3. Ассистент показывается только на первом шаге «Продукт» при заполнении `DRAFT` до отправки. На сервере проверять владельца и статус `DRAFT` перед вызовом модели; открытый в браузере шаг не является проверкой прав. После отправки, включая `NEEDS_INFO`, не вызывать модель. Контекст: три продукта, сохранённые цель и сумма собственной заявки, если они есть, актуальный подтверждённый расчёт, если он есть; без чужих заявок, секретов и содержимого файлов. Отсутствующий расчёт не заменять выдуманным. При первом открытии продукта цель и сумма могут отсутствовать: ассистент уточняет потребность в разговоре, перенос в форму требует действия клиента. При уходе с первого шага и возврате разговор сохраняется; объём отправляемого контекста ограничивать. Статусы, запросы и решения после отправки объясняются интерфейсом и сотрудником.
4. Ограничить ожидание модели: начальный предел одного ответа 60 секунд, одна генерация за раз для CPU-профиля. Второй одновременный запрос получает понятное сообщение о занятости. Это стартовые настройки; изменение после измерений фиксировать с Петей.
5. При сбое или превышении ожидания вернуть понятную ошибку ассистента; кредитный путь продолжает работать. Не выдавать справочный шаблон за ответ LLM.

### Дни 5–6: независимый запуск и исправления

1. Подготовить основной CPU-профиль: приложение, БД и Ollama запускаются на стороне проверяющих. Веса скачиваются при первом запуске и сохраняются в отдельном Docker volume — постоянном хранилище. Нужен явный индикатор или описание ожидания загрузки; её ошибка не маскируется готовностью ассистента.
2. Дополнительно описать подключение Ollama, установленной на компьютере Пети. Внутри Docker `localhost` указывает на сам контейнер; для Ollama на компьютере адрес другой. Оба способа реально проверить на используемой ОС, не обещать непроверенную универсальность.
3. Не публиковать порт Ollama в интернет. Доступ браузера к модели идёт через наш backend. Не открывать удалённый доступ к компьютеру Пети без отдельного согласования способа.
4. Измерить GPU-режим Пети и CPU-режим: первый ответ, повторные ответы, память всего проекта. Для CPU использовать профиль без переданного контейнеру GPU и подтвердить фактический режим, а не просто назвать его CPU.
5. Проверить T1–T6, перезапуск, чужой доступ и повторную отправку критичных действий. Запрещённые переходы статуса отклоняются. Подписание связано с принятой версией предложения.
6. Подготовить README, пример настроек без секретов, зафиксированные зависимости, модель данных, архитектурную схему, коллекцию запросов и перечень сторонних компонентов. Кира даёт бизнес-схему статусов, Настя — данные, Саша — описание скоринга.

## Что передать

- Работающий backend и согласованное описание API для Пети.
- Запуск проекта с чистого окружения и сохранением данных между перезапусками.
- Загружаемые синтетические данные T1–T6 и тестовые пользователи.
- Переключаемое подключение LLM и результаты измерений.
- Проверки критичных правил и инструкция для жюри без зависимости от компьютера Пети.

## Что решать самому

Внутреннюю организацию небольших модулей, подходящие библиотеки, хранение и техническую обработку ошибок в рамках выбранного стека. Фиксировать версии; не добавлять платную обязательную зависимость.

## Что согласовывать

API — с Петей. Поля и проверки — с Настей. Баллы — с Сашей. Ставки, ограничения, решения и статусы — с Кирой. Замену модели, увеличение требований к памяти, изменение времени ожидания и новый обязательный сервис — с Петей после измерений.

## Готовность

- [ ] Один клиент не читает и не меняет чужую заявку; действие сотрудника недоступно клиенту.
- [ ] Нельзя повторно выдать деньги или повторно провести оплату.
- [ ] Альтернатива и действия сотрудника соблюдают обязательные ограничения.
- [ ] Все T1–T6 проходят и переживают перезапуск.
- [ ] Локальная настоящая модель работает без платного сервиса и компьютера Пети.
- [ ] Остановка модели не ломает основной процесс.
- [ ] Другой участник запускает проект по инструкции без твоих устных подсказок.
