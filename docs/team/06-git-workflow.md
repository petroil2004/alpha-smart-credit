# Как команда работает с Git и GitHub

Общий порядок для пяти участников. Это наша договорённость для удобной разработки, а не дополнительное требование организаторов. Названия кнопок приведены для англоязычного интерфейса GitHub и могут немного отличаться.

## 1. Коротко: как сдаём свою работу

**Свежая main → новая ветка под одну задачу → изменения → осмысленные коммиты → Pull Request → проверка другим участником → объединение в main.**

`main` — общая принятая версия. В ней держим согласованные документы и проверенную основу приложения; в начале проекта там может быть только документация. Не держим результаты до шестого дня в пяти изолированных ветках. Незаконченный новый экран можно разрабатывать в своей ветке, не ломая общий рабочий путь.

Отдельная ветка `develop`, отдельные репозитории и личные копии проекта на GitHub вам сейчас не нужны. Работаете в одном уже созданном репозитории как collaborators — участники с доступом.

## 2. Слова, которые встретятся

| Слово | Что означает |
|---|---|
| Git | Программа, сохраняющая историю изменений файлов |
| GitHub | Сайт, где хранится общая копия проекта и обсуждаются изменения |
| Репозиторий | Файлы проекта вместе с их историей |
| Clone | Получить репозиторий с GitHub на компьютер вместе с историей |
| Ветка, branch | Место для отдельной задачи; можно менять файлы, не затрагивая main |
| Commit, коммит | Сохранённая порция изменений с автором, описанием и идентификатором |
| Push | Отправить локальные коммиты на GitHub |
| Fetch / pull | Получить сведения об обновлениях / получить и включить их в локальную ветку |
| Pull Request, PR | Предложение включить изменения своей ветки в другую; здесь — в main |
| Review | Проверка предложенных изменений другим участником |
| Merge | Объединение изменений веток |
| Конфликт | Ситуация, когда Git не может сам совместить правки; нужно выбрать правильный результат |
| Issue | Карточка задачи или ошибки на GitHub |
| Тег | Имя, закреплённое за конкретной версией, например `v0.1.0-hackathon` |

Коммит остаётся на компьютере до push. Создание PR ещё не включает изменения в main. Сохранение файла в редакторе само по себе не является коммитом.

## 3. Заливать ли эти инструкции в рабочий репозиторий

**Да.** В `docs/team/` храним задания и процесс работы; в `docs/superpowers/specs/` — общие договорённости; в `docs/business/` будут таблицы, правила и примеры аналитиков. Это документация проекта. Она помогает понять решения и соответствует ожидаемой организаторами проработке и истории работы.

Специально удалять её перед сдачей не нужно. Актуализируйте инструкции, если процесс изменился. Устаревший полезный документ можно пометить как исторический или перенести в `docs/archive/`, оставив ссылку на актуальную замену. Удаление файла обычным коммитом не удаляет его из истории. Не переписываем историю ради косметической «чистоты».

В репозиторий не кладём архивы этих же инструкций, `.DS_Store`, папки установленных зависимостей, локальные базы, журналы запуска, настоящие ключи и файлы весов модели. Архив из `output/` предназначен для пересылки людям; актуальные исходники документов — в `docs/`.

Файл `.env` с локальными настройками не загружаем. Пример без секретов `.env.example` загружаем, когда он будет создан. Шаблон `.gitignore` из комплекта помогает исключить типичные лишние файлы. Он не удаляет уже закоммиченные файлы: если секрет уже попал в историю, сообщить Пете/Вите и заменить секрет; обычного удаления недостаточно.

Прозрачная история важнее количества коммитов. Не создаём пустые коммиты для вида, не меняем даты и не приписываем себе чужую работу. Использование Codex само по себе разрешено по предоставленным ответам организаторов.

## 4. Как завести начальную документацию

Это делает Петя один раз.

1. Открыть существующий командный репозиторий. Не создавать второй проект вместо него.
2. Если репозиторий абсолютно пуст, создать первый README с названием и кратким описанием. Это единственное начальное исключение, когда первый файл создаётся прямо в основной ветке. Убедиться, что основная ветка называется `main`; если имя другое, согласовать единое имя и поправить инструкции, а не создавать вторую независимую историю.
3. От актуальной main создать ветку `codex/petya-team-docs`.
4. Добавить папку `docs/` из этого комплекта, сохранив вложенные папки, и `.gitignore`. Не загружать `output/` и служебную `.git/`.
5. Назвать коммит `docs(team): добавить задания и порядок работы команды`.
6. Открыть PR в main, попросить Витю проверить согласованность инструкций. После проверки объединить.
7. Остальные получают свежую main и создают свои ветки уже с общей документацией.

При последующем подключении проверено: репозиторий `petroil2004/alpha-smart-credit` был пустым. Рабочая папка Пети связана с ним через `origin`, первый README опубликован в main, документация подготовлена в ветке `codex/petya-team-docs`. Повторять инициализацию и заново добавлять origin Пете не нужно. Статус объединения документации проверяйте в PR на GitHub.

Остальные получают командный репозиторий через clone в свою папку. До отправки любой другой локальной копии проверить адрес и существующую историю. Не отправлять отдельную вновь созданную историю поверх командной. Реальная настройка удалённого доступа к репозиторию не меняет автоматически права других участников или защиту main.

## 5. Ветки: каждому своя задача

Имя: `codex/имя-задача`, латиницей, строчными буквами, слова через дефис. Имя помогает понять автора; ветка принадлежит задаче и после её завершения больше не используется.

| Участник | Пример первой ветки | Следующая отдельная задача |
|---|---|---|
| Петя | `codex/petya-client-draft` | `codex/petya-bank-view` |
| Витя | `codex/vitya-application-api` | `codex/vitya-ollama` |
| Настя | `codex/nastya-data-dictionary` | `codex/nastya-demo-cases` |
| Саша | `codex/sasha-scorecard` | `codex/sasha-score-examples` |
| Кира | `codex/kira-credit-policy` | `codex/kira-assistant-cases` |

Если задачу дорабатываем по замечаниям PR, продолжаем ту же ветку. После её объединения следующую задачу начинаем новой веткой от обновлённой main. Не создаём новую ветку на каждое исправление опечатки внутри текущей задачи.

Обычно одна задача занимает несколько часов или один день. Если задача больше, открыть Draft PR — черновик для ранней проверки. Каждый день обсуждать, можно ли выделить маленькую законченную часть. Не объединять заведомо сломанный код только ради ежедневного merge.

Петя меняет преимущественно сайт, Витя — сервер и запуск. Настя владеет материалами данных, Саша — скоринга, Кира — продуктов и решений. Если меняете чужой участок, сначала согласуйте. Ветки не защищают от смысловых противоречий автоматически.

## 6. Насте, Саше и Кире: путь через сайт GitHub

Терминал и Codex для редактирования документов не обязательны.

1. Открыть репозиторий и выбрать main в списке веток.
2. В этом списке ввести имя своей новой ветки и выбрать её создание от main. Проверить, что сверху теперь указана своя ветка.
3. Открыть нужный файл и нажать карандаш для редактирования. Для нового файла использовать `Add file` → `Create new file`, указав путь, например `docs/business/scoring.md`. Для загрузки подготовленного файла — `Upload files`, проверив папку назначения.
4. Проверить текст и нажать `Commit changes`. Написать осмысленное сообщение по разделу ниже. Если своя ветка уже создана, сохранить коммит в неё, не в main.
5. Для первого PR нажать `Compare & pull request` либо открыть раздел `Pull requests` → `New pull request`. Проверить: `base: main`, `compare: ваша ветка`.
6. Описать, что изменено, какие примеры проверены и кто нужен для согласования. Попросить проверяющего, указанного ниже.
7. Замечания исправлять в этой же ветке — PR обновится. Пока есть нерешённый вопрос, поставить Draft или написать, что объединять рано.
8. После проверки Петя или Витя объединяет PR. Для новой задачи снова выбрать свежую main и новую ветку.

Markdown (`.md`) — обычный текст с простым оформлением; GitHub показывает заголовки и таблицы. Для работы в LLM прикладывайте личное ТЗ, общие договорённости и актуальные материалы из main. Не просите LLM самостоятельно придумывать изменившиеся соседние правила.

## 7. Пете и Вите: путь на компьютере

Если копии репозитория ещё нет, сначала получить её через `git clone`, используя адрес из кнопки `Code` на GitHub. Например, в команде `git clone https://github.com/TEAM/REPO.git` слова TEAM и REPO заменить настоящими. Выполнять из родительской папки; не клонировать поверх уже существующей рабочей копии. Затем открыть полученную папку в Codex.

Настроить имя и email автора через GitHub Desktop или Git. Для одного проекта можно задать их локально командами `git config user.name` и `git config user.email` с собственными значениями. Email можно взять из настроек приватного адреса GitHub. Не ставить всем участникам имя Пети и не менять глобальные настройки без необходимости. Для доступа использовать обычную авторизацию GitHub; не записывать токен в URL репозитория.

### Начало новой задачи

В командах ниже один сквозной пример: Петя загружает общую документацию в ветке `codex/petya-team-docs`. Для другой задачи подставляйте её ветку, пути и описание.

```bash
git status
git switch main
git pull --ff-only origin main
git switch -c codex/petya-team-docs
```

Сначала `git status` должен показать отсутствие незакоммиченных изменений. Если они есть, не переключать ветки вслепую: закончить и сохранить текущую работу либо обратиться к Codex для её безопасного сохранения. Не использовать удаляющие команды для «очистки».

`--ff-only` обновляет main только без дополнительного объединения историй. Если команда не выполнилась, остановиться и разобраться с Петей/Витей; не заменять её принудительной отправкой.

### Сохранение и отправка работы

```bash
git status
git diff
git add docs .gitignore
git diff --cached
git commit -m "docs(team): добавить задания и порядок работы команды"
git push -u origin codex/petya-team-docs
```

Перед этими командами перенести подготовленные `docs/` и `.gitignore` в правильную локальную копию командного репозитория. Команды выполняются из его корня, когда эти файлы уже существуют. В другой задаче выбирать только её файлы, а не всю папку `docs/`. Codex может выполнить команды за вас после проверки текущего состояния.

`git diff` показывает правки; новые ещё не добавленные файлы видны в `git status` и читаются отдельно. `git add` выбирает файлы коммита; `git diff --cached` показывает выбранное. В кодовой задаче до коммита выполнить подходящие проверки приложения и записать их результат. Для обычного текста — перечитать смысл, таблицы, ссылки и примеры; не добавлять искусственный тест только ради теста.

Не используем привычку `git add .`: легко захватить чужие правки или лишние файлы. Выбираем нужные пути. После первого push обычный `git push` отправляет новые коммиты текущей связанной ветки. Затем открываем PR на GitHub.

### Если main обновилась, пока вы работаете

Сохранить свою работу коммитом в своей ветке и получить обновления:

```bash
git fetch origin
git merge --no-edit origin/main
```

Если merge прошёл, повторить проверки и отправить ветку. Если появился конфликт, перейти к разделу о конфликтах. Не делать merge из main с несохранёнными локальными правками. В нашей схеме не нужны rebase, `push --force` и переписывание уже отправленных коммитов.

В одной локальной папке не запускаем два независимых Codex-чата, которые одновременно переключают ветки и пишут файлы. Самый простой вариант — один активный исполнитель на рабочую копию; отдельные параллельные задачи требуют отдельных рабочих копий и согласованного разделения файлов. У Пети и Вити на разных компьютерах естественно будут разные копии.

## 8. Сообщения коммитов

Используем облегчённый Conventional Commits:

```text
тип(область): конкретно что изменено
```

Ключевое слово на английском; описание можно по-русски. Область полезна, но необязательна. Тип выбираем по смыслу изменения, а не по имени автора.

| Тип | Когда применять | Пример |
|---|---|---|
| `feat` | Новое поведение работающего продукта | `feat(applications): добавить ответ на запрос сведений` |
| `fix` | Исправление ошибки | `fix(overdraft): запретить оплату сверх лимита` |
| `docs` | Документы, задания, описание правил | `docs(data): уточнить единицы финансовых показателей` |
| `test` | Только проверки приложения | `test(scoring): проверить значение на границе диапазона` |
| `build` | Сборка и зависимости приложения | `build(docker): добавить CPU-запуск Ollama` |
| `ci` | Автоматические проверки на GitHub | `ci: запускать проверки при открытии PR` |
| `refactor` | Перестройка кода без изменения поведения | `refactor(scoring): разделить расчёт и объяснения` |
| `chore` | Вспомогательное обслуживание проекта | `chore: исключить локальные файлы из Git` |

Основных трёх слов `feat`, `fix`, `docs` хватит для большинства задач. Если проверки идут вместе с новой функцией, можно сохранить их в том же `feat`-коммите: не нужно отделять каждую мелочь. Документ о скоринге — `docs(scoring)`, реализованный расчёт — `feat(scoring)`.

Один коммит — одна понятная порция работы, например правило и его проверка. Не один коммит за все шесть дней и не коммит на каждую строку. Названия `update`, `final`, `final2`, `правки` не объясняют изменения. Не создавать пустые коммиты для статистики.

Если меняем API так, что прежний frontend перестаёт работать, это несовместимое изменение. Сначала согласовать с Петей и Витей; в названии допустимо выделить `!`, например `feat(api)!: изменить формат предложения`, и описать переход. Символ не исправляет несовместимость автоматически.

`Closes #12` в описании PR используем только если задача №12 действительно существует и полностью решена. `Refs #12` — просто ссылка на задачу. Такие ссылки необязательны; не нужно заводить карточку на каждую опечатку.

## 9. Проверка и объединение PR

Название PR пишем в том же стиле, что коммит. Описание — четыре коротких пункта: что и зачем изменено; как проверено; что нужно смежному участнику; какие ограничения остаются.

| Автор | Кто проверяет |
|---|---|
| Петя: код интерфейса | Витя проверяет связь с сервером; Кира/Настя принимают смысл своих экранов |
| Витя: backend и запуск | Петя проверяет пользовательский путь; владелец правил принимает расчёты |
| Настя | Саша и Кира проверяют смысл; Витя проверяет возможность обработки |
| Саша | Кира проверяет использование оценки; Настя — данные и единицы |
| Кира | Саша проверяет связь с риском; Витя — расчёты и переходы; Петя — интерфейс |

Не требуется три формальные подписи на каждый PR. Нужен хотя бы один другой человек, проверивший изменение; при изменении чужих правил — также ответ затронутого владельца. Достаточно комментария с перечислением проверенного, если кнопка Approve недоступна. Собственный PR автор не принимает в одиночку.

После проверки Петя или Витя выполняет **Create a merge commit** (обычное Merge pull request). Выбрали этот способ, чтобы сохранить отдельные коммиты ветки и этапы работы. Squash объединяет их в один; он не запрещён организаторами, но для этого проекта не является нашим основным способом. Не включаем требование линейной истории, которое противоречило бы merge-коммитам.

Перед объединением проверить отсутствие нерешённых замечаний и конфликтов; для кода — результаты нужных проверок. После объединения перепроверить затронутый путь в общей версии. Затем можно удалить ветку на GitHub: коммиты, вошедшие через merge, и обсуждение PR сохраняются. Рабочая main обновляется командой `git pull --ff-only origin main` из main при чистом рабочем каталоге.

По возможности Петя настраивает защиту main: изменения через PR, одна проверка другим участником, запрет принудительной отправки и удаления основной ветки. Доступность зависит от настроек и тарифа GitHub. Если технической защиты нет, тот же порядок соблюдаем командной договорённостью. Эти настройки данным документом не включаются автоматически.

## 10. Конфликты и ошибки

Если Git или GitHub сообщает о конфликте, не выбирать автоматически «оставить всё моё» или «оставить всё чужое». Обсудить с автором другой правки ожидаемый общий результат.

Петя/Витя или их Codex объединяет корректные части, проверяет отсутствие меток `<<<<<<<`, `=======`, `>>>>>>>`, затем повторяет проверки, делает коммит и отправляет ветку. Аналитик может попросить помощи и подтвердить смысл итогового текста. Для отмены незавершённого merge существует `git merge --abort`; использовать после проверки состояния. Не пытаться лечить конфликт командой `reset --hard`.

Ошибка после merge исправляется новым коммитом и небольшим PR. При необходимости отмены целого изменения использовать согласованный revert — новый коммит отмены. Не удалять чужие коммиты, не менять общую историю и не применять `push --force` без отдельного разбора.

## 11. Перед дедлайном

Петя и Витя выбирают проверенный коммит main, фиксируют его полный hash — уникальный идентификатор версии — и при необходимости тег `v0.1.0-hackathon`. Если тег с таким именем уже есть, не перемещать его: выбрать другое имя и записать его. Проверить, что версия и все нужные файлы отправлены на GitHub и доступны жюри.

README должен описывать именно сдаваемую версию. После дедлайна не выдаём новые изменения за часть зафиксированной сдачи. Обычные рабочие коммиты и честные исправления допустимы в истории; они показывают процесс. Красивые префиксы не заменяют работающий продукт и проверку.

## 12. Готовый запрос для Codex

> Прочитай docs/team/06-git-workflow.md, общие договорённости и моё личное ТЗ. Сначала проверь текущую ветку, незакоммиченные изменения, remote и состояние main. Для новой задачи используй отдельную ветку codex/имя-задача от актуальной main. Не трогай чужие изменения. Выполни одну согласованную задачу, проверь результат и покажи изменения. При сохранении выбирай только относящиеся к задаче файлы и используй осмысленный префикс коммита. Если прошу отправить работу, сделай push только своей ветки и открой PR в main; merge оставь для проверки другим участником. Не применяй force push и не переписывай историю. Если текущая ситуация не позволяет безопасно продолжить, объясни конкретную причину.

Запрос задаёт порядок будущей работы. Подготовка инструкции сама по себе не означает, что коммиты, push, PR, защита веток или публикация уже выполнены.
