# Настя: данные, проверки и демонстрационные истории

**Актуализация 23.10.2026.** При сверке словаря используй обязательность по действиям из application-fields.md. Для окончательного решения нужны шесть последних завершённых месяцев с фиксированием периода при отправке; неполнота финансовых данных не запрещает подачу. Клиентские уточнения не становятся банковскими фактами без проверки сотрудника. Общая [спецификация согласования](../superpowers/specs/2026-10-23-credit-policy-alignment-design.md), [каталог](../business/product-catalog.md), [поля](../business/application-fields.md), [правила решений](../business/decision-rules.md) имеют приоритет над первоначальными формулировками задания ниже. Их нужно передавать LLM вместе с материалами своей задачи.

## Зачем нужна твоя работа

Сделать так, чтобы одинаковые сведения понимались одинаково во всём проекте. Например, «1,5 млн рублей» должно превратиться в понятную сумму, а отсутствие сведений о долге не должно означать нулевой долг.

Твоя прежняя задача «препроцессинг» сохраняется. Простыми словами, это проверка и приведение данных к согласованному виду. Писать код не нужно: ты готовишь таблицы и примеры для Вити, затем проверяешь реализацию. Помогать с анализом может обычная LLM.

Сначала прочитай [общие договорённости](../superpowers/specs/2026-10-21-credit-cabinet-design.md).

## Как передавать работу через GitHub

Используй [Git-инструкцию](06-git-workflow.md), особенно раздел «Насте, Саше и Кире: путь через сайт GitHub». Терминал не нужен. Создай от свежей main ветку `codex/nastya-data-dictionary`, сохрани туда словарь и примеры, открой PR в main. Для последующей отдельной задачи с демонстрационными историями — новая ветка `codex/nastya-demo-cases` после обновления общей версии.

Примеры коммитов: `docs(data): описать поля и единицы`, `docs(data): добавить шесть демонстрационных историй`. Саша и Кира проверяют смысл, Витя — возможность обработки. После согласования Петя или Витя объединяет PR. Замечания текущего PR исправляй в его ветке; после merge новую задачу начинай от main. Не редактируй самостоятельно чужие правила ради совпадения результата. Подробности коммитов и конфликтов — в общей инструкции.

## Что сделать

### 1. Составить словарь данных

В первый день подготовить таблицу. Одна строка — одно поле. Столбцы:

| Поле | Зачем нужно | Откуда берём | Вид и единица | Когда обязательно | Проверка | Ошибка для клиента | Пример |
|---|---|---|---|---|---|---|---|
| Желаемая сумма | Расчёт и подбор | Ввод клиента | Рубли | До отправки | Положительное число; ограничения продукта проверяются отдельно | «Укажите сумму больше нуля» | 500 000 |
| Платежи по действующим долгам | Оценка нагрузки | Синтетические сведения банка | Рубли в месяц | До оценки нагрузки | Неотрицательное; неизвестно не равно 0 | Если источник не ответил, это не ошибка ввода клиента | 40 000 |

Обязательные группы: профиль компании; цель, сумма и срок; шесть месяцев финансовых показателей; текущие обязательства; имитация кредитной истории и регистрации; ожидаемое поступление для овердрафта. Не заставлять клиента повторно вводить весь банковский профиль.

Поступления не называем прибылью. Операционные расходы не содержат платежей по кредитам. Сумма долга и ежемесячный платёж по нему — разные поля. Период и единица всегда видны. Данные по действующим обязательствам приходят из синтетического профиля и проверки; пользовательское уточнение не превращается автоматически в подтверждённый факт.

### 2. Подготовить правила приведения и проверки

Для каждого случая указать исходный ввод, ожидаемый результат и понятное сообщение. Минимум 12 примеров:

- «1 500 000» и «1500000»;
- отрицательная и нулевая сумма;
- пустое обязательное поле;
- неизвестное значение и подтверждённый ноль;
- месяцы вместо дней овердрафта;
- ожидаемое поступление раньше текущей даты;
- ожидаемое поступление меньше предполагаемого возврата;
- разные финансовые периоды;
- пропущенный месяц;
- расходы выше поступлений;
- противоречащие друг другу сведения пользователя и синтетической проверки.

Свободный текст «1,5 млн» в чате ассистента может требовать уточнения. Не обещать распознавание любых форматов в числовом поле: с Петей согласовать, какие формы ввода действительно поддерживаются.

Различать три ситуации: ошибка формата, корректное неблагоприятное значение и техническая недоступность источника. Например, расходы больше поступлений — повод для оценки риска, а не ошибка формата. Недоступный источник нельзя исправить просьбой к клиенту «введите правильную кредитную историю».

### 3. Сделать шесть согласованных демонстрационных историй

Использовать ID из общих договорённостей:

| ID | Что подготовить |
|---|---|
| T1 | Полный профиль компании для обычного оборотного кредита |
| T2 | Профиль с потребностью в оборудовании |
| T3 | Профиль, где первоначальная сумма велика, но существует допустимая альтернатива |
| T4 | Корректно отправленная заявка, где для решения не хватает дополнительных сведений; подготовить и данные для последующего ответа |
| T5 | Профиль с подтверждённым основанием для отказа, согласованным с Кирой |
| T6 | Короткий кассовый разрыв — временный недостаток денег; ожидаемое поступление и сумма оплаты поставщику |

Все имена, идентификаторы, финансовые показатели, сотрудники и документы вымышленные. При необходимости проверки формата ИНН согласовать синтетические значения с Витей: не подставлять реальные компании для удобства.

У каждой истории: компания, пользователь, помесячные показатели, долги, ответ имитации внешних проверок, запрос клиента, ожидаемый балл от Саши и решение от Киры. Если точные баллы ещё не готовы, не выдумывать их: передать входы Саше и затем заполнить совместно. К концу второго дня итоговая таблица должна быть полной.

### 4. Описать имитацию внешних проверок

Для проверки регистрации и кредитной истории подготовить простую таблицу «профиль → ответ». Отдельно описать вариант недоступности источника. Ответы должны повторяться при повторном запуске, а не меняться случайно.

Для T4 подготовить вымышленное пояснение или небольшой TXT/PDF, который клиент сможет приложить. Автоматически читать и распознавать документ не требуется. Все вложения явно обозначить как демонстрационные.

### 5. Проверить приложение

После реализации Витей и Петей пройти примеры через интерфейс. Проверить, что суммы, периоды, пропуски и ошибки сохраняются правильно. Саша проверяет расчёт баллов, Кира — решение; ты проверяешь исходные и подготовленные данные.

## Что передать и когда

| Срок | Результат | Кому |
|---|---|---|
| Середина дня 1 | Первая версия словаря и по одному профилю обычного кредита и овердрафта | Саша, Кира, Витя, Петя |
| Конец дня 1 | Согласованные поля и правила проверки | Витя, Петя |
| Конец дня 2 | Шесть полных историй, примеры ошибок, ответы внешних проверок, вложение для T4 | Витя; Саша и Кира проверяют смысл |
| Дни 3–5 | Результаты проверки приложения: ожидание, факт, способ повторить ошибку | Петя и Витя |

Предлагаемые рабочие файлы в репозитории: `docs/business/data-dictionary.md`, `docs/business/input-examples.md`, `docs/business/demo-cases.md`. Если удобнее сначала таблица в документе, это допустимо; Витя переносит согласованную версию в проект. Структурированные файлы для загрузки создаёт его Codex, ты проверяешь значения.

## Как работать с обычной LLM

Можно дать ей запрос:

> Помоги составить словарь данных для демонстрационного кредитного кабинета. Используй только три согласованных продукта и приложенные общие договорённости. Для каждого поля объясни смысл, источник, единицу, обязательность и проверку. Не добавляй реальные персональные данные и банковские интеграции. Отдельно покажи неизвестное значение, ноль и техническую ошибку источника. Проверь, что платежи по долгам не включены в операционные расходы.

После ответа проверь каждую строку: кто и зачем использует поле? Ненужные поля убрать, нужные для скоринга и решения сверить с Сашей и Кирой.

## Что решать самой

Имена вымышленных компаний, оформление таблиц, дополнительные случаи ошибок и последовательность исследования. Предлагать упрощение, если поле нигде не используется.

## Что согласовывать

Новые обязательные поля, единицы и финансовый смысл — с Сашей и Кирой; показ и ввод — с Петей; поддерживаемые форматы и ответы внешних проверок — с Витей. Не менять самостоятельно кредитные пороги и исходы историй.

## Готовность

- [ ] У каждого используемого поля есть смысл, источник и единица.
- [ ] Неизвестное значение отличается от нуля; техническая ошибка — от плохого показателя.
- [ ] T1–T6 содержат проверенные входы, баллы и решения.
- [ ] Показатели не учитываются дважды и относятся к согласованному периоду.
- [ ] Витя может реализовать обработку по примерам без догадок.
- [ ] Проверены ввод, сохранение и повторное открытие данных в приложении.
