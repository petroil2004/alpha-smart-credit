## Нормативная сводка: поля и обязательность по действиям

Этот раздел конкретизирует таблицы ниже. «Обязательно» всегда относится к указанному действию. Сохранение `DRAFT` допускает отсутствие любого редактируемого значения; заполненное значение обязано иметь корректный формат и не превышать технические пределы. Плохая нагрузка не является ошибкой формата.

Калькулятор платежа обычного кредита требует только продукт, сумму и срок; финансовые показатели нужны для предварительной оценки доступности, а не для самой формулы платежа. Для овердрафтных процентов нужны планируемая оплата и дни; проверка лимита по обороту и покрытия возврата выполняется отдельно. Даже при неполных финансовых данных известные расчёты показываются, а результат доступности обозначается как «нужны сведения».

Для финансовой части нужны шесть последних **завершённых календарных месяцев**; при подаче 23.10.2026 — апрель–сентябрь 2026. До отправки период показывается явно, при отправке фиксируется в заявке и не сдвигается при уточнениях в следующем месяце. Для каждого месяца отдельно сохраняются поступления, операционные расходы и источники значений; неизвестное остаётся null, а не нулём. Возраст бизнеса считается полными месяцами на дату подачи.

Синтетические банковские сведения и ответы проверок сохраняют свой источник. Уточнение клиента записывается отдельно как SELF_REPORTED; для принятия в окончательный расчёт сотрудник проверяет его, фиксирует исходные/уточнённые значения, основание и время. Официальные регистрационные данные клиент сам не переписывает. Файл не распознаётся автоматически и не заменяет структурированные поля.

Формат вложений — синтетические PDF/TXT до 5 МиБ на файл, только по запросу; сервер проверяет право загрузки и скачивания. Для T4 достаточно одного неизвестного месяца расходов: корректная отправка → запрос месяца → клиент указывает значение и при необходимости прикладывает файл → сотрудник сверяет → повторная оценка той же заявки.

Маршрут: продукт → параметры → проверка. На параметрах после расчётов находится текстовая цель; профиль, дополнительные параметры и финансовые сведения — в соответствующих блоках, сводка и предварительная оценка — перед отправкой. Это логические этапы, не требование создавать отдельную страницу для каждого поля. Работает автосохранение и завершающее «Сохранить и выйти». Ассистент необязателен для прохождения пути и не записывает изменения без действий клиента.

Точные JSON-имена **новых** полей, пути API и миграции будут согласованы перед кодом. Таблица задаёт смысл и обязательность; она не объявляет несуществующие поля реализованными. Существующий контракт черновика не меняется этим документом.

## 1. Профиль компании и доступ

Вход выполняется через заранее созданные тестовые аккаунты. Обязательные роли — клиент и кредитный специалист; наблюдателя и регистрацию новых клиентов не реализуем. Клиент видит профиль и заявки своей компании, каталог и калькулятор. Сервер проверяет роль, принадлежность компании и допустимость действия; каталог и калькулятор до входа отложены.

## 2А. Подбор кредитного продукта

Первый шаг показывает продукты и необязательную плашку помощника под ними. Клиент выбирает самостоятельно или описывает задачу в разговоре с будущим ассистентом. В обоих случаях клиент **подтверждает выбранный продукт**; отдельного обязательного переключателя режима нет. ИИ может предложить продукт, но не одобряет заявку, не назначает ставку и не меняет выбор без согласия.

## 2Б. Кредитный калькулятор

### 5.1. Расчётные формулы

| Правило | Формула / смысл | Примечание |
| --- | --- | --- |
| Аннуитетный платёж | P × r/(1 − (1+r)^(-n)); r = годовая ставка / 12 / 100 | — |
| Овердрафт: проценты | Использованная сумма × (годовая ставка/100) × дни / 365 | — |
| Опер. поток | Средние поступления − средние расходы (без выплат по долгам) | — |
| Свободный новый платёж | MAX(0; MAX(0; опер. поток) × 50% − платежи по текущим долгам) | — |
| Лимит по оборотам | MIN(лимит каталога; 30% от среднемесячных поступлений) | — |
| Покрытие овердрафта | Ожидаемое поступление ≥ сумма использования + проценты; дата в срок | — |

Для обычных кредитов промежуточные результаты не обрезать, денежные итоговые значения отображать в копейках. Для овердрафта проценты рассчитываются за указанные дни исходя из 365 дней в году при неизменной сумме использования. Денежные результаты округляются по ROUND_HALF_UP; подробности упрощённого аннуитета — в decision-rules.md. Точную реализацию проверяет Витя.

## 7. Контроль перед коммитом / интеграцией

- [ ] Проверить тестовый вход, роли клиента и специалиста, недоступность чужой компании через API; не включать гостевой режим в обязательный объём.
- [ ] Убедиться, что все значения проходят клиентскую **и серверную** валидацию, а неизвестные финансовые данные не превращаются в нули.
- [ ] Сверить лимиты, сроки и ставки с `product-catalog.md`, а финансовые пороги и исходы — с `decision-rules.md`.
- [ ] Подтвердить с Настей поля и источники (`BANK_DATA`, `SELF_REPORTED`, синтетические проверки), с Сашей — входы скоринга.
- [ ] Проверить с Витей формулы, округление, проверку даты возврата овердрафта и воспроизводимость ответов моков.
